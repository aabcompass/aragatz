# Клиент Aragatz: захват, проверка и измерение передачи

Клиент использует только стандартную библиотеку Python 3.9+. Он совместим с
опубликованным протоколом v1: команда 32 байта, ответ 64 байта. Заголовок и
команда содержат big-endian `uint32`, полезная нагрузка передаётся как неизменные
байты DDR в little-endian. Формат описан в
[capture_tcp_v1.md](../docs/capture_tcp_v1.md). Прошивка и клиент должны быть из
одной ревизии ветки; ранний вариант с заголовком 192 байта несовместим.

## 1. Сначала штатный echo

Настройте адреса платы и ПК по инструкции
[PS-приложения](../ps_sw/lwip_capture/README.md). Примеры ниже предполагают
`192.168.10.10` на плате. Сначала загрузите отдельное штатное приложение lwIP Echo
Server и проверьте скорость/дуплекс/линк PHY в UART. Затем выполните:

```sh
python3 host/aragatz_client.py echo 192.168.10.10 --port 7
```

По умолчанию это 16 обменов по 1024 байта с проверкой каждого байта. Для более
длинной проверки можно задать `--rounds 1000 --bytes 4096`. Это проверка пути
TCP, а не измеритель пропускной способности и не тест ядра захвата в PL.

## 2. Захват и сохранение на ПК

После отдельной проверки echo загрузите приложение захвата с разрешённым
`ARAGATZ_ENABLE_CAPTURE`. Тесты ядра остаются отдельным приложением.

```sh
python3 host/aragatz_client.py status 192.168.10.10
python3 host/aragatz_client.py capture 192.168.10.10 --frames 64 --prev 16 --fragments 16 --output capture_001.bin
python3 host/aragatz_client.py verify capture_001.bin
```

Клиент принимает один завершённый захват, проверяет CRC32, все 96 слов каждого
кадра в режиме COUNTER, преамбулы каждого фрагмента, ID, AUX и padding, порядок
timestamp, расписание триггеров и признак чистого END без AXI busy/ошибок. Затем
он сохраняет файл и `capture_001.bin.json`, повторно читает оба с диска и снова
проверяет данные. Только после успешного чтения и проверки отправляется ACK,
разрешающий прошивке освободить буфер для следующего START.

Границы параметров: `frames >= 2`, `0 <= prev <= 64`, `prev < frames`,
`1 <= fragments <= 16`. Размер
`fragments * (128 + 768 * frames)` плюс 256-байтовый guard должен помещаться
в резерв DDR размером 1 MiB. Клиент проверяет это до отправки START. Настройки
по умолчанию дают 788480 байт полезной нагрузки.

Файлы публикуются целиком после `flush`/`fsync`; существующие имена по умолчанию
отклоняются до сетевого обмена. Для намеренной замены задайте `--overwrite`.
Для режима без перезаписи используется атомарное создание hard link в том же
каталоге; подходят обычные локальные файловые системы Linux и NTFS. Если
файловая система это не поддерживает, сохранение завершится ошибкой и ACK не
будет отправлен: выберите другой локальный каталог и сделайте FETCH. Два файла
не образуют одну атомарную транзакцию: при сбое между публикацией `.bin` и
`.json` может остаться только первый; новый FETCH следует сохранить под другим
именем. На Windows выполняется `fsync` файлов, но Python не предоставляет
переносимый способ `fsync` каталога.

JSON сохраняет все 16 полей заголовка и дополнительный объект
`capture_metadata` с UTC-временем и измеренными интервалами приёма/проверки.
Команда `verify` повторно проверяет CRC заголовка из JSON и полный буфер. Она
поддерживает и прежний JSON, содержащий только поля заголовка.

## 3. Восстановление после разрыва или ошибки записи

Прошивка сохраняет готовый буфер до корректного ACK. Если ошибка возникла до
отправки ACK, запросите STATUS и заберите буфер по его ID:

```sh
python3 host/aragatz_client.py status 192.168.10.10
python3 host/aragatz_client.py fetch 192.168.10.10 17 --output recovered_017.bin
```

Вместо `17` подставьте фактический `id` из STATUS; `state=2` означает RETAINED.
FETCH передаёт буфер, затем клиент выполняет тот же цикл проверки/сохранения/ACK.
На новой TCP-сессии сначала требуется получить DATA через FETCH: отдельного
обходного ACK в клиенте нет. ID действителен только до перезапуска прошивки.

Если разрыв произошёл при отправке ACK или получении его ответа, клиент не
может знать, был ли ACK принят. STATUS после подключения определяет состояние:
EMPTY означает, что буфер уже освобождён, RETAINED — что его можно повторно
получить. Не перезапускайте плату, пока нужен сохранённый в DDR буфер.

`--timeout 30` задаёт тайм-аут отсутствия сетевого прогресса, а не общий лимит
времени команды. Ошибка CRC/COUNTER или записи не разрешает новый захват.

## 4. Скорость выгрузки: повторная передача неизменного буфера

```sh
python3 host/aragatz_client.py bench 192.168.10.10 --frames 64 --prev 16 --fragments 16 --repeats 100 --output bench_seed.bin --report bench.json
```

`bench` делает один START, проверяет и сохраняет исходный буфер, затем выполняет
ровно `--repeats` запросов FETCH этого же ID. Каждый ответ проходит CRC32,
полную проверку COUNTER и побайтное сравнение с исходным буфером. Исходный START
не входит в агрегированные сетевые интервалы. После всех повторов сохраняется
отчёт, исходный файл ещё раз проверяется, и только затем отправляется один ACK.
При ошибке проверки ACK не отправляется.

Это изменение относительно первого черновика клиента: `bench` больше не делает
новый захват на каждой итерации. Для исследования полного цикла нового захвата
используйте отдельные вызовы `capture` с разными выходными именами.

Отчёт имеет `schema="aragatz.benchmark.v1"`, `mode="retained_fetch"`, параметры
захвата, данные исходного START и список всех измерений FETCH. Раздел `aggregate`
содержит суммарные байты и интервалы:

| Поле | Что измеряет |
|---|---|
| `payload_seconds` | От получения полного заголовка до последнего байта payload |
| `request_seconds` | От начала отправки FETCH до последнего байта payload |
| `verified_seconds` | От начала FETCH до окончания проверки payload в памяти |
| `wall_seconds` | Всё время цикла FETCH, включая Python, сравнение буферов и вывод |

В `rates` вычисляется `sum(bytes) / sum(interval)`, с отдельными значениями
`MB_per_s` (10⁶ байт/с), `MiB_per_s` (2²⁰ байт/с) и `Mbit_per_s` (10⁶ бит/с).
`wall_rate` использует `wall_seconds`. Не усредняйте скорости отдельных
итераций арифметически. Поле `cycle_seconds` верхнего уровня дополнительно
охватывает исходный START, сохранение, все повторы, запись отчёта и ACK; финальная
перезапись отчёта с результатом ACK в этот интервал не входит.

Для отдельной команды `capture` результат в stdout включает `cycle_seconds`
и `cycle_rate`: от начала START/FETCH до успешного ответа на ACK, включая
проверку, сохранение и чтение с диска. Это скорость всего прикладного цикла,
отличная от сетевой скорости.

Интервал `payload_seconds` измеряется на стороне Python: часть данных может
уже находиться в TCP-буфере ОС к моменту начала чтения. На небольшом буфере его
результат может завысить физическую скорость линии. Для оценки выгрузки
сопоставляйте `request_seconds` по множеству FETCH, результаты штатного TCP perf
example и скорость согласованного линка. Эти измерения не содержат времени
финального TCP ACK на стороне платы: текущий 64-байтовый протокол не передаёт
такую метрику. Python-проверка всех слов может существенно ограничить
`verified_seconds` и `wall_rate`.

Числа скорости платы пока не измерены. Поток 307,2 МБ/с превышает даже номинальные
125 МБ/с линии 1 Гбит/с; этот режим предназначен для конечного захвата с паузой
на передачу. Методика стендовых измерений находится в
[ethernet_measurement.md](../docs/ethernet_measurement.md).

## 5. Проверки клиента без платы

Из корня репозитория:

```sh
python3 -m unittest discover -s host -p 'test_aragatz_client.py' -v
```

Тесты проверяют повреждённые заголовки/данные, CRC, полное содержимое COUNTER,
границы параметров, отказ от перезаписи, ошибки диска, порядок сохранение → ACK,
восстановление через FETCH и цикл измерений. Реальные loopback TCP-сокеты
проверяют взаимодействие с моделью платы и разбиение потока на части. При
наличии GCC дополнительно собирается C-тест сервера прошивки; его реальный
64-байтовый заголовок и payload проверяются независимым Python-клиентом.
Это проверки программной логики, а не Vivado/Vitis-сборка и не аппаратная
проверка Ethernet.
