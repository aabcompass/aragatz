# Скорость выгрузки Aragatz → ПК

**Фактическая скорость платы пока не измерена.** В этой задаче речь о передаче
из DDR платы на ПК. Скорость обратного направления проверяют отдельно.
Поддержка KSZ9031 и проверка ядра Capture — независимые этапы:
успех одного не заменяет проверку другого.

## Какие результаты нужны

| Испытание | Что оно подтверждает |
|---|---|
| MDIO + negotiated link + штатный echo | PHY/RGMII/GEM/TCP работают в обе стороны |
| Штатный lwIP TCP Perf Client → iperf2 | Длительная передача PS→PC без участия Capture |
| Aragatz START/FETCH + CRC/COUNTER | Скорость выгрузки реального завершённого буфера и его сохранность |
| Полный цикл capture | Время захвата, cache/CRC, передачи, проверки, диска и ACK |

Echo не является измерением однонаправленной пропускной способности.
Показание линка 1000 Мбит/с также не равно полезной скорости TCP.

## Зафиксировать стенд

Для сравнения нужны commit приложения, SHA-256 XSA/bitstream, фактические
checkout RTL, версия Vitis/BSP, оптимизация компилятора и включённый cache.
Сохраните UART, MDIO address/ID, согласованную скорость и duplex, настройки
платы и ПК, модель NIC, ОС, MTU, прямой кабель/коммутатор.

Сохраните сгенерированный `lwipopts.h`: `TCP_MSS`, `TCP_SND_BUF`,
`TCP_SND_QUEUELEN`, `TCP_WND`, `MEM_SIZE`, `MEMP_NUM_TCP_SEG`,
`PBUF_POOL_SIZE`, checksum offload. Изменяйте один параметр за раз.
Размеры TCP buffers должны быть согласованы с памятью и числом сегментов;
сам по себе большой `TCP_SND_BUF` не гарантирует рост скорости.

На Linux negotiated link можно посмотреть через `ethtool <interface>`;
на Windows — через `Get-NetAdapter` и свойства сетевого адаптера.
Это дополнительное наблюдение скорости линка, не результат benchmark.

## 1. Независимый сетевой эталон PS→PC

После успешного echo создайте **отдельное** приложение
`lwIP TCP Perf Client` из Vitis 2023.1 с тем же квалифицированным PS/GEM/PHY BSP.
Аппаратная регрессия и Capture во время этого теста не запускаются.

На ПК используется **iperf2**, совместимый со штатным примером. README
тега `xilinx_v2023.1` описывает Iperf 2.0.5; iperf3 имеет другой протокол.

```bash
iperf -s -i 5 -w 2M
```

В `tcp_perf_client.h` задайте:

- `TCP_SERVER_IP_ADDRESS`: адрес ПК, например `192.168.10.20`;
- `TCP_CONN_PORT=5001`;
- `TCP_TIME_INTERVAL=60` для первого минутного запуска;
- `INTERIM_REPORT_INTERVAL=5`.

IP и MAC платы задаются в `main.c` этого примера. Повторите тест несколько
раз, при необходимости увеличьте длительность до 300 секунд. Сохраните
промежуточные и итоговые показания обеих сторон, ошибки и link changes.
Сопоставляйте настройки BSP: результат настроенного perf-примера не переносится
автоматически на приложение с другими pools/window/checksum.

Источник команд и параметров:
[AMD/Xilinx TCP Perf Client, 2023.1](https://github.com/Xilinx/embeddedsw/blob/xilinx_v2023.1/lib/sw_apps/lwip_tcp_perf_client/src/README.txt).

## 2. Повторы одного сохранённого захвата

После запуска Capture ELF:

```bash
python3 host/aragatz_client.py bench 192.168.10.10 --frames 64 --prev 16 --fragments 16 --repeats 100 --output bench_seed.bin --report bench.json
```

Benchmark делает **один START**, проверяет и сохраняет исходный буфер,
затем выполняет 100 FETCH того же ID. Каждый повтор проверяется по CRC32,
всем словам COUNTER и побайтовому совпадению с исходным буфером.
В конце сохраняется отчёт и отправляется один ACK. Новый захват
не запускается между повторами; это исключает его время из FETCH-метрик.

Исходный файл записывается и перечитывается перед повторами и ещё раз
проверяется перед ACK. Каждый FETCH заново на диск не записывается.
Для полного сценария с диском используйте отдельные команды `capture`
с разными выходными именами.

Отчёт имеет `schema=aragatz.benchmark.v1`, `mode=retained_fetch`.
Раздел `aggregate` исключает первоначальный START:

| Поле | Начало → конец | Практический смысл |
|---|---|---|
| `payload_seconds` | Полный header → последний байт payload | Скорость приёма в Python |
| `request_seconds` | Начало FETCH → последний байт payload | Выгрузка одного буфера с запросом/header |
| `verified_seconds` | Начало FETCH → полная проверка в памяти | Выгрузка плюс работа проверяющего кода |
| `wall_seconds` | Весь цикл повторов | Также сравнение буферов, вывод и loop overhead |
| `cycle_seconds` верхнего уровня | START → финальный ACK | Исходный захват, диск, все FETCH, запись отчёта и подтверждение |

Финальная перезапись отчёта после ACK не включена в `cycle_seconds`.
Отдельный `capture` печатает собственные `cycle_seconds/cycle_rate`,
включающие сохранение и повторное чтение файла. Разные интервалы нельзя
обозначать одним словом «скорость» без уточнения.

Все сводные скорости считаются как **сумма байтов / сумма времён**.
Не усредняйте арифметически скорости отдельных коротких итераций:

```text
MB/s   = bytes / seconds / 1_000_000
MiB/s  = bytes / seconds / 1_048_576
Mbit/s = bytes / seconds * 8 / 1_000_000
```

У отчёта явные поля `MB_per_s`, `MiB_per_s`, `Mbit_per_s`.
Скорость `payload_seconds` иногда оказывается завышенной: часть буфера
уже находится в очереди ОС после чтения header. Поэтому для вывода о сети
сопоставляйте `request_seconds`, длительный iperf2 и negotiated link.
Python-проверка всех слов может ограничивать `verified_seconds/wall_rate`.
Текущий 64-байтовый протокол не передаёт время последнего TCP ACK,
измеренное на PS; таких значений в отчёт не подставляют.

## 3. Приёмка целостности и восстановления

До публикации результата скорости на плате выполните:

1. Один фрагмент, затем 16; CRC и все слова COUNTER совпадают.
2. Обрыв на середине DATA; STATUS/FETCH на новом соединении возвращают тот же ID.
3. START при RETAINED отклоняется и не меняет буфер.
4. Неверные ID/длина/CRC в ACK не разрешают повторное использование DDR.
5. Отключение/подключение кабеля восстанавливает echo, затем FETCH.
6. Аппаратная ошибка или timeout приводят к FAULT и запрещают повторный START.
7. После верного ACK следующий захват получает новый ID и проходит проверку.

Для отрицательных сценариев используйте отдельные файлы и сохраняйте UART.
Повреждённый файл сам по себе не доказывает сетевую ошибку: разделите результаты
по CRC payload, рисунку COUNTER, сохранению/перечитыванию и статусам Capture.

## Ограничение входного потока

По текущим настройкам генератора:

```text
200_000_000 × 24 / 125 × 8 = 307_200_000 байт/с
                            = 307,2 MB/s
                            = 2457,6 Mbit/s
```

| Согласованный Ethernet link | Номинальная верхняя граница до накладных расходов |
|---:|---:|
| 10 Мбит/с | 1,25 MB/s |
| 100 Мбит/с | 12,5 MB/s |
| 1000 Мбит/с | 125 MB/s |

Полезная скорость TCP ниже номинальной. Даже идеальный 1 GbE не переносит
непрерывный вход 307,2 MB/s без потери данных. Двойной буфер сглаживает паузы,
но не устраняет устойчивое превышение входа над выходом.

После измерения полезной скорости `R` время одной выгрузки оценивается как
`payload_bytes / R`, а время полного цикла берётся из отдельного capture.
Для будущей непрерывной работы потребуется меньший средний входной темп,
выбор событий/децимация, накопление с конечным горизонтом или другой интерфейс.
Эта ветка реализует конечный захват с последующей выгрузкой.
